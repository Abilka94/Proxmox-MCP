# Gap Analysis: Task Mutation (Phase 1C)

> Дата: 2026-06-06
> Статус: Завершён

## Текущее состояние проекта

На момент Phase 1C проект имеет:

- HTTP клиент (`PveClient`) на базе httpx (без proxmoxer)
- Инструменты task domain только на чтение:
  - `task_status` — получение статуса задачи
  - `task_log` — получение лога задачи
  - `task_wait` — ожидание завершения задачи
  - `task_list` — список задач ноды
- Read-only инструменты кластера:
  - `cluster_status`, `cluster_resources`, `cluster_tasks`
- Собственный класс ошибок `PveError`
- Базовое audit-логирование
- Нет JobStore
- Нет mutate-операций

## Детальный анализ разрывов

### GAP-1: Отсутствие tool `task_cancel`

**Описание:** Нет MCP-инструмента для остановки запущенной задачи по UPID.

**Влияние:** Критическое. Task domain неполон — пользователь может прочитать статус и лог задачи, но не может на неё повлиять.

**Требования:**
- Принимает `upid` (string) и `node` (string)
- Выполняет POST-запрос к PVE API
- Возвращает результат операции
- Опционально ожидает завершения (wait)

**Затраты:** Средние (1 новый tool, 1 новый метод в PveClient)

---

### GAP-2: Отсутствие POST-метода в PveClient

**Описание:** `PveClient` реализует только `_get_json()` для GET-запросов. Для task_cancel требуется POST.

**Влияние:** Критическое. Необходимый фундамент для всех будущих mutate-операций (Phase 2+).

**Требования:**
- Добавить `_post_json(endpoint, data=None, json=None)` в `PveClient`
- Обработка ошибок POST через `PveError`
- Интеграция с существующим audit-логированием

**Затраты:** Малые (1 новый метод)

---

### GAP-3: Отсутствие защиты от повторной отмены

**Описание:** Нет механизма, предотвращающего повторный вызов task_cancel для уже завершённой или уже отменяемой задачи.

**Влияние:** Среднее. Повторный вызов приведёт к ошибке PVE API, которая будет возвращена пользователю.

**Требования:**
- Проверять статус задачи перед отменой
- Возвращать понятную ошибку, если задача уже завершена

**Затраты:** Малые (проверка статуса + сообщение об ошибке)

---

### GAP-4: Отсутствие двухфазной модели отмены

**Описание:** Нет разделения между "запрос на отмену отправлен" (cancel_requested) и "задача отменена" (cancelled).

**Влияние:** Среднее. Без JobStore двухфазная модель нереализуема в полном объёме.

**Требования:**
- Минимально: возвращать статус UPID после запроса на отмену
- В перспективе: JobStore с полной моделью статусов

**Затраты:** Малые (для минимальной реализации)

---

### GAP-5: Отсутствие параметра wait для task_cancel

**Описание:** Нет возможности дождаться завершения задачи после отправки запроса на отмену.

**Влияние:** Среднее. Пользователь вынужден вызывать task_wait отдельно.

**Требования:**
- Добавить опциональный параметр `wait` (bool, default: false)
- При `wait=true` вызывать существующий `task_wait` после отмены

**Затраты:** Малые (использование существующего task_wait)
