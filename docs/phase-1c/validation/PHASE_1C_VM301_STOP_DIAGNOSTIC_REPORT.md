# Phase 1C — диагностика остановки VM 301

> Дата: 2026-11-09; время в отчёте — Europe/Moscow (UTC+03:00)
> Нода: 7500T; VM: 301 phase1c-cancel-test
> Метод: только GET через существующий PveClient

## Заключение

**Наиболее вероятное объяснение: VM перестала работать при перезапуске/новой загрузке ноды 7500T 6 ноября и затем не была запущена автоматически.** Запуск VM 3 ноября подтверждён task/syslog, перед загрузкой ноды имеются активные метрики VM, а onboot в конфигурации не задан и имеет default=0 в установленной схеме.

Однако **непосредственная причина завершения процесса VM и причина перезапуска хоста достоверно не установлены**. В доступных данных нет прямой записи «VM 301 остановлена вследствие reboot», задачи остановки или kernel/OOM/panic события, привязанного к её процессу. Нельзя утверждать доказанную ручную остановку, отключение питания, OOM, crash либо действие task_cancel. Связь с загрузкой хоста — обоснованная гипотеза по совокупности фактов, не установленная точная причина.

## Объём и безопасность

Прочитаны правила документации и индекс проекта; отчёт помещён в validation/. [Предыдущая проверка прав/статуса](PHASE_1C_ADMINISTRATOR_PERMISSIONS_CHECK_REPORT.md) зафиксировала stopped; [сценарий B](PHASE_1C_TEST_TASK_SELECTION_REPORT.md) не запускался.

Явно загружен config/local.yaml: endpoint https://192.168.0.178:8006, PolicyMode READ_ONLY, существующий verify_ssl=false. Использованы штатный PveClient и ограниченный GET-only HTTP transport, без redirects и изменения конфигурации. Нодальные запросы направлялись только на 7500T; глобальный cluster/log прочитан без изменений. Авторизация не выводилась. Конфигурация VM изучалась в памяти, в отчёт включены только диагностические поля; токены, headers и секреты отсутствуют.

Все **22 сетевых GET завершились HTTP200**, включая две загрузки установленной apiSchema. Источники: задачи VM/ноды, task status/log, current status/config/pending, RRD, cluster log, time/status/config ноды, syslog и установленная API-схема. Локальная попытка преобразовать время через zoneinfo обнаружила отсутствие tzdata; ничего не устанавливалось, преобразование epoch выполнено с явным UTC+03:00. GET /nodes/7500T/time подтвердил timezone Europe/Moscow.

Никаких POST/PUT/PATCH/DELETE, запуска/остановки VM, qmshutdown/task_cancel, ACL, смены PolicyMode, исходников, commit/push/tag не было. После диагностики выполнены только документ и навигация.

## История задач VM 301

GET /nodes/7500T/tasks?vmid=301&source=all&limit=500 вернул **2 записи**. Каждая дополнительно проверена GET status/log; журналы содержат по одной строке TASK OK.

| Операция | Начало | Завершение из task list | Пользователь | task status | exitstatus |
|---|---|---|---|---|---|
| qmcreate, VMID 301 | 2026-11-03 00:10:04 | 2026-11-03 00:10:04 | root@pam | stopped | OK |
| qmstart, VMID 301 | 2026-11-03 00:12:00 | 2026-11-03 00:12:00 | root@pam | stopped | OK |

UPID создания:

```text
UPID:7500T:00327888:0FBD1966:6AE8FC2C:qmcreate:301:root@pam:
```

UPID запуска:

```text
UPID:7500T:003279EF:0FBD46B5:6AE8FCA0:qmstart:301:root@pam:
```

Совпадают node=7500T, id=301 и типы операций. status=stopped у **qmstart task** означает завершение операции запуска; это не означает остановку запущенной VM. Его exitstatus=OK подтверждает успешное окончание старта.

В возвращённой истории VM нет qmstop/qmshutdown/qmreboot/отмены. Это отсутствие записей в доступной task history, не универсальное доказательство, что процесс не мог завершиться без task либо что не было утраты старых журналов.

## RRD, автозапуск и текущая конфигурация

GET /nodes/7500T/qemu/301/rrddata?timeframe=week&cf=MAX вернул 336 точек; у 176 есть ненулевые CPU/RAM/I/O показатели. Последняя активная точка имеет epoch **1793970000 = 2026-11-06 16:00:00 +03:00**, CPU около 0.0643 и RAM около 34.8 MB. Это согласуется с работающей VM до загрузки хоста в 16:13:50.

RRD — агрегированные интервальные метрики (в этой выборке примерно 30 минут), поэтому timestamp точки не является точным временем остановки, а отсутствие дальнейших метрик само по себе не доказывает причину. Точный интервал завершения QEMU по этому источнику не устанавливается.

GET config/pending: имя phase1c-cancel-test, memory=512 MiB, cores=1, balloon=0, boot=order=ide2, ide2=none,media=cdrom. onboot отсутствует; установленная apiSchema для onboot указывает default=0. Следовательно, текущая конфигурация не предусматривает автоматический запуск VM после загрузки хоста. Это объясняет сохранение stopped после restart, но не доказывает, что конфигурация была точно такой же во все прошлые моменты.

HA: current status возвращает managed=0. Hookscript/lock/agent/acpi в просмотренной config-сводке не заданы; отсутствие поля не приравнивается к явному false, кроме отдельно подтверждённого default onboot. Полного исторического config audit через API не получено.

## Что установлено и что неизвестно

**Подтверждено:** VM создана и успешно запущена 3 ноября; после запуска были активные метрики; 6 ноября нода загрузилась заново; текущий onboot default=0; после этой загрузки startall завершён, новый qmstart для VM301 не найден; сейчас VM stopped.

**Наиболее вероятно:** остановка/утрата QEMU-процесса связана с завершением предыдущего сеанса хоста, а VM осталась stopped из-за отключённого автозапуска.

**Неизвестно:** точный момент и непосредственный механизм завершения VM, причина перезапуска ноды, наличие неотражённого внешнего воздействия перед reboot. Доказательств qmshutdown/task_cancel, ручного VM stop, guest shutdown, OOM либо конкретной аппаратной ошибки не найдено. Ни одну из этих причин нельзя объявить установленной.

Для более строгого установления причины нужны дополнительные сохранённые журналы предыдущей загрузки или сведения оператора о событиях/питании 6 ноября; это не повод автоматически изменять ноду или запускать тест. Текущая диагностика завершена, VM не запускалась. Создан отчёт и обновлена навигация; дальнейшие действия не выполняются.
