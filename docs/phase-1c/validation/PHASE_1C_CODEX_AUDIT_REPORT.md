Некоторые страницы документации на `pve.proxmox.com` вернули HTTP 403; использованы доступные официальные исходники. Проверенные ветки — изменяемые источники, а не снимок пакетов установленной системы.

Правильный запрос:

```http
DELETE /api2/json/nodes/{node}/tasks/{url_encoded_upid}
Authorization: PVEAPIToken=USER@REALM!TOKENID=SECRET
```

Тело не требуется. Схема возвращаемого значения — `null`; при успешной обработке ожидаются HTTP 200 и `{"data":null}`. Операция выполняется на целевой ноде. Для чужой задачи проверяется `Sys.Modify` на **`/nodes/{node}`**. Для собственной задачи эта проверка не требуется. Невалидный UPID и отсутствие task-файла обрабатываются как ошибки параметра. Это подтверждено [Tasks.pm](https://github.com/proxmox/pve-manager/blob/master/PVE/API2/Tasks.pm).

В [stable-8](https://github.com/proxmox/pve-manager/blob/stable-8/PVE/API2/Tasks.pm) также зарегистрирован DELETE. Оснований считать `/status/stop` необходимым для PVE 8.x нет.

Если worker уже не работает, `check_worker` возвращает управление без остановки; следовательно, повторный DELETE может успешно завершиться, пока task-файл существует и права достаточны. Для работающего worker реализация посылает TERM группе процессов, затем предусматривает KILL. Это вывод из [RESTEnvironment.pm](https://github.com/proxmox/pve-common/blob/master/src/PVE/RESTEnvironment.pm), а не результат live-проверки.

HTTP 200 подтверждает обработку запроса, но **не доказывает причинную связь между запросом и завершением задачи**.

Предоставленный пользователем вывод `pvesh usage` согласуется с исходниками. Самостоятельно на установленном PVE 9.2.21 он не воспроизводился; DELETE через MCP и API token остаётся непроверенным.

## 3. Critical — блокирующие замечания

### C1. Неверный endpoint и HTTP-метод

Участок: `src/mcp_proxmox/domains/tasks/service.py:264`, вызов на строке 285.

Код формирует `/tasks/{upid}/status/stop` и вызывает `_post_json()`.

Последствия: основная функция Phase 1C не соответствует зарегистрированному API. Предварительный HTTP 501 объясняется неверной комбинацией маршрута и метода; он не доказывает отсутствие остановки задач в PVE 9.

Решение: DELETE `/nodes/{node}/tasks/{upid}` через метод клиента.

### C2. Ошибка ожидания превращается в успешную остановку

Участок: `src/mcp_proxmox/domains/tasks/service.py:305`, формирование результата на строках 315–321.

`task_wait()` возвращает `completed=false` и `error` при некоторых ошибках API. `task_cancel()` проверяет только `timed_out`; любой другой результат объявляет:

```json
{
  "status": "stopped",
  "cancel_requested": true,
  "stopped": true
}
```

**Подтверждено локальным воспроизведением:** preflight `running`, успешный замокированный mutate-вызов, затем HTTP 403 при чтении статуса → возвращены `status="stopped"` и `stopped=true`.

Решение: подтверждать наблюдаемое завершение только при `completed is True` и `status == "stopped"`. Ошибки ожидания сохранять как ошибки, отдельно от результата отправки запроса.

### C3. Tool недоступен при любой валидной конфигурации

Участки:

- `src/mcp_proxmox/config/models.py:16`: существует только `READ_ONLY`.
- `config/schema/config.schema.json:24`: `const: READ_ONLY`.
- `src/mcp_proxmox/policy/engine.py:44`: запрещены все tier, кроме READ.
- `src/mcp_proxmox/mcp/registry/tools.py:657`: `task_cancel` правильно имеет `OPERATOR`.

Последствия: даже исправленный DELETE нельзя штатно вызвать через MCP.

Решение: согласовать ограниченный режим `OPERATOR`, синхронно обновить модель, схему и матрицу авторизации. Сохранить `READ_ONLY` по умолчанию. Режим OPERATOR должен разрешать READ/OPERATOR и запрещать ADMIN. Простое добавление enum без изменения проверки создаст возможность пропуска ADMIN.

UPID кодируется через `urllib.parse.quote(..., safe="")` — это правильное направление. Но percent encoding не заменяет проверку структуры UPID и соответствия `node`. Следует принимать исходный UPID, кодировать один раз и покрыть token-owned UPID тестом.

Есть также ограничение времени: `task_wait` в `src/mcp_proxmox/domains/tasks/service.py:91` проверяет timeout между запросами; запрос и sleep могут выйти за оставшийся бюджет. Текущий `timeout` не является строгим ограничением полной длительности `task_cancel`, включая preflight и DELETE.

## 5. HTTP-клиент и Minor

В `src/mcp_proxmox/pve/client/core.py:255`:

- `TimeoutException` перехватывается после его базового `RequestError`; специальная ветка таймаута недостижима.
- Ошибка разбора JSON не преобразуется в `PveApiError`.
- При создании собственного `AsyncClient` отсутствует явное закрытие. Аналогичный долг есть в GET.
- `PveApiError.details` содержит ответ сервера, но `__str__()` его не показывает: MCP получает общий текст без содержательной причины.
- Неопределённый исход mutate при потере ответа не представлен отдельно.

Рекомендуется исправить обработку таймаутов и некорректных ответов, определить владение HTTP-клиентом и безопасно передавать структурированные диагностические сведения. Автоматический retry mutate не добавлять.

Minor:

- Описание `wait=false` как «немедленного» ответа неточно: preflight и сам DELETE требуют времени; отсутствие polling не гарантирует мгновенного возврата.
- `docs/phase-1c/implementation/PHASE_1C_IMPLEMENTATION_REPORT.md:145` содержит несогласованную арифметику: `6+7+1=14`, тогда как итоговая строка указывает 9.
- Дизайн использует `poll`, реализация — `poll_interval`; встречаются устаревшие пути файлов и название `PveError` вместо `PveApiError`.

## 6. Безопасность и права

Текущий запрет OPERATOR в READ_ONLY работает и подтверждён тестом. Снижать tier до READ нельзя.

Особенности token authentication:

- Идентичность токена — полный `user@realm!tokenname`.
- Задача пользователя и задача его токена не обязательно считаются собственными для одного и того же вызывающего субъекта.
- Для separated privileges эффективные права — пересечение прав пользователя и токена; для full privileges действуют права пользователя. Это подтверждает [руководство pveum](https://github.com/proxmox/pve-docs/blob/master/pveum.adoc).

Токены не требуют CSRF; `protected` означает передачу выполнения привилегированному daemon, а не обязательную ticket-authentication. DELETE не запрещает токены явно, а регистрация методов разрешает их по умолчанию. Это подтверждают [HTTPServer.pm](https://github.com/proxmox/pve-manager/blob/master/PVE/HTTPServer.pm) и [RESTHandler.pm](https://github.com/proxmox/pve-common/blob/master/src/PVE/RESTHandler.pm).

Следовательно, рекомендация предыдущего отчёта сразу расширить права токена преждевременна: сначала нужно установить владельца тестовой задачи. Для чужих задач требуется отдельная проверка разрешений.

Отмена PVE task не является откатом операции. Безопасность зависит от типа прерываемой задачи и её побочных эффектов. JobStore или универсальный workflow для Phase 1C не требуются.

## 8. Предлагаемые изменения архитектуры и дизайна

Для `_delete_json()` есть прямое обоснование: это необходимый транспортный примитив текущей операции. Желательно предоставить домену публичный метод наподобие `stop_task(node, upid)`, который строит путь и вызывает `_delete_json()`. Домен должен управлять preflight и ожиданием, а клиент — HTTP и API-путями.

**Сохранение `_post_json()` технически возможно, но для Phase 1C не требуется.** Рекомендуется убрать его из обязательного объёма фазы, если отдельного согласованного потребителя нет. Сохранение как будущего фундамента требует явного решения; оно не исправляет отмену задач. Универсальный транспортный framework сейчас избыточен.

Предлагаемая семантика контракта:

| Поле | Значение |
|---|---|
| `cancel_requested` | Получен успешный ответ на DELETE в текущем вызове |
| `status` | Последний наблюдаемый статус либо `unknown` |
| `stopped` | Подтверждено наблюдением `status=stopped` |
| `exitstatus` | Значение PVE без переинтерпретации в «отменено» |
| `timed_out` / `error` / `reason` | Машинное объяснение результата |

При неизвестном исходе транспорта нельзя достоверно утверждать ни принятие, ни непринятие запроса. Форму представления этого случая нужно согласовать. Отдельный статус `cancelled` без доказательств вводить не следует.

9. Проверить повторный вызов и уже завершённую задачу.
10. Проверку чужой задачи и дополнительных ACL выполнять только при отдельном разрешении и необходимости.
11. Зафиксировать HTTP-ответ, MCP-результат, наблюдаемый статус, `exitstatus`, длительность и последствия.
12. Не использовать SSH, kill, ticket-auth или альтернативные маршруты как автоматический fallback.

## 11. Достоверность и нерешённые вопросы

**Подтверждено локальным кодом и проверками:** состояние Git, три блокирующие ошибки, недостатки валидации и контракта, 150 успешных тестов, отсутствие содержательных integration/contract suites, воспроизведение ложного `stopped=true`.

**Подтверждено официальными исходниками:** DELETE-маршрут, аналог в stable-8, схема `null`, проверки владельца и ACL, token/CSRF-модель, механизм остановки worker.

**Не подтверждено live:** успешный DELETE через MCP и текущий токен на PVE 9.2.21, фактические ACL и принадлежность выбранной задачи, поведение конкретных типов задач после отмены, полная совместимость установленного PVE 8.x.

Утверждения прежних отчётов об обязательности POST, невозможности отмены в PVE 9 и необходимости SSH не имеют достаточного основания. Утверждение о работе reference-реализации на PVE 8 также нельзя считать доказанным по одному наличию вызова в её коде.

Исправления не начаты. Требуется согласование результатов аудита и предложенного контракта Phase 1C.
