# Правила рабочего процесса проекта

> Дата: 2026-06-06
> Статус: Утверждено

## Жизненный цикл фаз

Каждая фаза разработки проходит строгую последовательность этапов:

1. **Comparative Analysis** — сравнительный анализ референсных реализаций
2. **Gap Analysis** — анализ различий и определение объёма работ
3. **Design** — проектирование архитектуры и интерфейсов
4. **Review** — рецензирование и согласование дизайна
5. **Implementation** — реализация (только после согласования дизайна)
6. **Validation** — валидация (unit-тесты, live validation)
7. **Acceptance** — формальная приёмка фазы
8. **Commit** — фиксация изменений в репозитории
9. **Tag** — создание аннотированного тега

Переход к следующему этапу возможен только после завершения предыдущего.

---

## Правила реализации

- **Запрещено** начинать реализацию до согласования дизайна (Review).
- **Запрещено** создавать commit и tag до завершения Acceptance.
- Изменения в коде допускаются только в рамках этапа Implementation.
- На этапах Comparative Analysis, Gap Analysis, Design, Review допускается только документация.

---

## Правила документации

- Начиная с **Phase 1C** вся новая документация ведётся на **русском языке**.
- **Не переводятся:**
  - имена файлов и директорий
  - пути
  - MCP tool identifiers (например, `task_status`, `task_cancel`)
  - API endpoints (например, `/nodes/{node}/tasks/{upid}/status`)
  - названия фаз (Phase 1A, Phase 1B.1 и т.д.)
  - код и shell-команды
- Ранее созданная документация на английском языке не требует перевода, если она уже принята.

---

## Правила репозитория

- Коммиты оформляются на **русском языке**.
- Аннотации тегов оформляются на **русском языке**.
- Сообщение коммита должно отражать суть изменений, а не быть пустым или шаблонным.
- Каждый тег должен соответствовать завершённой и принятой фазе.

---

## Правила совместимости

- **Primary Target:** Proxmox VE **9.x**
- **Secondary Target:** Proxmox VE **8.x** (best effort)
- При конфликте между PVE 9.x и PVE 8.x приоритет всегда отдаётся PVE 9.x.
- Если функция доступна только в PVE 9.x, она не должна эмулироваться или упрощаться для PVE 8.x.
- Если функция работает на обеих версиях, её поведение должно быть идентичным.

---

## Правила Comparative Analysis

**Обязателен** для следующих категорий задач:

- mutate операции (task_cancel, stop, shutdown и т.д.)
- backup/snapshot
- create/delete ресурсов
- operator layer (управление доступом, привилегии)
- job store (фоновые задачи, retry, отмена)
- workflow engine (многошаговые сценарии)

**Не обязателен** для:

- локальных bugfix
- документации (правила документирования выше)
- мелких read-only функций (если не затрагивают архитектуру)

---

## Правила Validation

- При возможности выполнять **live validation** на реальном кластере.
- Unit-тесты **не заменяют** live validation.
- Live validation выполняется на минимально необходимом наборе операций для подтверждения корректности.
- Результаты live validation фиксируются в отчёте.
- Если live validation невозможна (отсутствие кластера, ограничения доступа), это должно быть явно указано в отчёте с обоснованием.

## Структура директории фазы

```
docs/phase-{X}/
├── comparative-analysis/   # Comparative Analysis (если обязателен)
│   └── COMPARISON_*.md
├── gap-analysis/           # Gap Analysis
│   └── GAP_ANALYSIS_*.md
├── design/                 # Design документы
│   └── PHASE_{X}_DESIGN.md
├── review/                 # Review заметки (если есть)
├── implementation/         # Implementation отчёты
│   └── PHASE_{X}_IMPLEMENTATION_REPORT.md
├── validation/             # Validation планы и отчёты
│   ├── PHASE_{X}_LIVE_VALIDATION_PLAN.md
│   └── PHASE_{X}_LIVE_VALIDATION_REPORT.md
└── acceptance/             # Acceptance документ
    └── PHASE_{X}_ACCEPTANCE.md
```
