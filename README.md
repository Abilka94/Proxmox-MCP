# MCP-Proxmox

Сервер Model Context Protocol (MCP) для чтения инфраструктуры Proxmox VE и контролируемой отмены задач.

## Возможности

### Кластер
- Статус кластера, кворум, состав узлов

### Узлы
- Список узлов с состоянием online/offline
- Использование ресурсов узла (CPU, memory, disk, uptime)

### Виртуальные машины
- Инвентаризация ВМ с выделенными ресурсами
- Состояние ВМ в рантайме (CPU, memory, disk I/O, balloon)
- Конфигурация ВМ

### Контейнеры (LXC)
- Инвентаризация контейнеров
- Состояние контейнера в рантайме
- Конфигурация контейнера

### Хранилища
- Инвентаризация пулов хранения
- Статус и использование хранилищ
- Содержимое хранилищ

### Сеть
- Список сетевых интерфейсов узла

### Обновления
- Доступные обновления пакетов на узле
- Сводка обновлений по кластеру

### Задачи
- Список задач с фильтрацией (status, type, user, VMID)
- Статус задачи (UPID → status, exit status)
- Журнал задачи (инкрементальный, со смещением start)
- `task_wait` — ожидание завершения задачи с таймаутом и exponential backoff
- `task_follow` — ожидание с инкрементальным накоплением журнала (макс. 5000 строк)
- `task_cancel` — запрос остановки задачи с необязательным наблюдением результата

## MCP-инструменты

**22 инструмента** в 9 доменах. По умолчанию сервер работает в режиме `READ_ONLY`.

### Кластер
- `server_info` — идентификация и конфигурация сервера
- `cluster_info` — статус и кворум кластера

### Узлы
- `list_nodes` — список всех узлов с состоянием
- `node_status` — детальное использование ресурсов узла

### Виртуальные машины
- `vm_list` — инвентаризация ВМ
- `vm_status` — состояние ВМ в рантайме
- `vm_config` — конфигурация ВМ

### Контейнеры
- `container_list` — инвентаризация LXC-контейнеров
- `container_status` — состояние контейнера в рантайме
- `container_config` — конфигурация контейнера

### Хранилища
- `storage_list` — инвентаризация пулов хранения
- `storage_status` — использование и статус хранилища
- `storage_content` — содержимое хранилища

### Сеть
- `network_list` — сетевые интерфейсы узла

### Обновления
- `node_updates` — доступные обновления на узле
- `cluster_updates` — сводка обновлений по кластеру

### Задачи
- `task_list` — история задач с фильтрацией
- `task_status` — статус задачи по UPID
- `task_log` — журнал задачи
- `task_wait` — ожидание завершения задачи (таймаут, backoff)
- `task_follow` — ожидание с накоплением журнала
- `task_cancel` — запрос остановки задачи через DELETE; OPERATOR, Phase 1C принята с ограничениями

## Установка и подключение MCP

Требуются Python **3.12–3.14**, доступ к HTTPS API Proxmox VE и API-токен с правами на нужные ресурсы. Установите проект из checkout релиза:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e .
```

Сервер запускается командой `python -m mcp_proxmox` и общается с MCP-клиентом через **stdio**. В настройках клиента укажите абсолютный путь к Python из окружения, рабочий каталог проекта и переменные окружения:

| Переменная | Назначение |
|---|---|
| `MCP_PROXMOX_CONFIG` | Путь к YAML-конфигурации; по умолчанию `config/default.yaml` относительно рабочего каталога |
| `PVE_HOST` | HTTPS URL API вашего Proxmox VE |
| `PVE_TOKEN_ID` | Полный идентификатор `USER@REALM!TOKENID` |
| `PVE_TOKEN_SECRET` | Секрет токена, передаваемый через защищённые настройки окружения клиента |

Шаблон подключения: [deploy/mcp-client.example.json](deploy/mcp-client.example.json). Замените демонстрационные значения своими. [config/default.yaml](config/default.yaml) использует перечисленные переменные и включает проверку TLS. Файл `.env` автоматически не загружается: его значения необходимо экспортировать в окружение запускающего процесса. Локальные конфиги с credentials исключены из Git и не должны публиковаться.

## Режимы безопасности

| `policy.mode` | READ-инструменты | `task_cancel` (OPERATOR) | ADMIN-инструменты |
|---|---|---|---|
| `READ_ONLY` — default | Разрешены | Запрещён до HTTP | Запрещены |
| `OPERATOR` — явное включение | Разрешены | Разрешён | Запрещены |

**`ADMIN` — зарезервированный уровень инструментов, а не поддерживаемый режим конфигурации v0.4.0.** Неизвестный mode отклоняется. Для включения отмены администратор явно меняет `policy.mode` в выбранном локальном конфиге на `OPERATOR` и перезапускает MCP-процесс. MCP-инструмента переключения режима нет. Локальная политика не расширяет ACL Proxmox: при разделении привилегий токен ограничен также правами пользователя.

Для собственной задачи API проверяет владельца, включая token identity. Для остановки чужой задачи требуются `Sys.Modify`, а для чтения её статуса/журнала — `Sys.Audit` на `/nodes/{node}`. Автоматического назначения прав нет.

## Использование task_cancel

Инструмент отправляет один `DELETE /nodes/{node}/tasks/{upid}` после предварительного GET статуса. Если задача уже завершена, DELETE не отправляется. Аргументы:

| Параметр | Тип / ограничения | По умолчанию |
|---|---|---|
| `upid` | Обязательная исходная строка UPID, без предварительного URL encoding | — |
| `node` | Обязательная нода, совпадающая с нодой в UPID | — |
| `wait` | boolean: наблюдать завершение после принятия запроса | `false` |
| `timeout` | integer, 1–3600 секунд; бюджет наблюдения после DELETE | `120` |
| `poll_interval` | Конечное число, 0.1–30 секунд | `1.0` |

Неизвестные аргументы и числовые строки не принимаются. Пример JSON-RPC вызова; UPID ниже демонстрационный — используйте реальный идентификатор разрешённой задачи:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "task_cancel",
    "arguments": {
      "upid": "UPID:pve1:00000001:00000001:00000001:test::operator@pve!mcp:",
      "node": "pve1",
      "wait": true,
      "timeout": 20,
      "poll_interval": 1
    }
  }
}
```

MCP возвращает JSON результата в `content[].text`. Проверяйте машинные поля, включая `error`, а не только успешный JSON-RPC ответ:

- `cancel_requested=true` — API подтвердил запрос; `false` — не отправлен или явно отклонён; `null` — исход неизвестен.
- `status=stopped` и `stopped=true` — наблюдается завершение задачи; это не универсальное доказательство отмены именно этим запросом. `exitstatus` передаётся из PVE.
- При `wait=false` после принятия DELETE возвращаются `status=unknown`, `stopped=null`, без polling. При `wait=true` выполняются ограниченные GET-наблюдения.
- `timed_out=true` означает исчерпание бюджета наблюдения, не доказательство продолжающейся работы задачи. Preflight/DELETE имеют отдельные HTTP-таймауты, поэтому полное время вызова может быть больше `timeout`.
- `error` содержит безопасные `code`, `phase`, `http_status`, `detail`. Невалидный, пустой или потерянный ответ не считается подтверждением; только ожидаемый `data:null` подтверждает DELETE для task_cancel.

Автоматического повтора DELETE нет. При неизвестном исходе сначала проверяйте состояние READ-инструментами. Новый явный вызов для running задачи может отправить новый DELETE; дедупликации и rollback нет. Отмена worker не гарантирует откат уже выполненных действий над ресурсами.

## Ограничения релиза

Phase 1C принята с ограничениями: полный Live L1–L5 проверен на PVE **9.2.21**, отрицательные HTTP/timeout/race сценарии — локально. Реальная цепочка конкретного desktop MCP-клиента с отменой и PVE8 не валидированы live. Обычные структурированные логи не являются неизменяемым audit store.

Используйте доверенный сертификат API; отключение TLS verification не рекомендуется. Проверка релиза выполнялась с широкими ранее назначенными правами, поэтому она не доказывает минимальную ACL-конфигурацию. Исторический security-риск, прежние Ruff/mypy ошибки и остальные ограничения описаны в [Closure Report](docs/phase-1c/acceptance/PHASE_1C_CLOSURE_REPORT.md). Номер этого milestone определяется Git-тегом; встроенная package/runtime metadata пока сохраняет прежнее значение `0.1.0-alpha.0`.
